## Описание проекта

Проект **Shop Database** — backend на **Django + Django REST Framework** для работы с заказами в магазине.

Ключевая бизнес-операция: **добавление товара (ItemInOrder) в заказ (Order)**.

Также в проекте есть сидирование тестовых данных (категории/товары/клиент/заказы) — **автоматически запускается только при `DEBUG=True`**.

## Как запустить

### Запуск через Docker Compose (рекомендуется)

1. Создайте файл `.env` в корне репозитория (рядом с `docker-compose.yml`) и задайте переменные:

- `SECRET_KEY` — секретный ключ Django
- `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD` — доступ к Postgres
- `DEBUG` — `True` или `False`

2. Соберите и запустите сервисы:

```bash
docker compose up --build
```

3. Сервис работает и готов принимать заказы!

- **API** доступно на `http://localhost:8000/api/`

## API документация

### POST `/api/add-to-order/`

Добавляет товар в заказ. Если товар уже есть в заказе — увеличивает его количество.

**Request body (JSON):**

- `order_id` (int, >= 1) — ID заказа
- `article_id` (int, >= 1) — ID товара
- `quantity` (int, >= 1) — количество

Пример:

```json
{
  "order_id": 1,
  "article_id": 10,
  "quantity": 2
}
```

**Response 200 (JSON):**

Возвращает созданную/обновлённую позицию заказа:

- `id` — ID позиции
- `article` — название товара
- `order` — ID заказа
- `price_in_order` — цена на момент добавления
- `quantity` — количество в заказе
- `total_price` — сумма по позиции

## Комментарий автора

Проект сделан как компактный пример **service-layer подхода**: логика добавления
товара в заказ вынесена в `OrderService`, а API-слой (DRF) остаётся тонким.

Главные дилеммы при разработке проекта:
1. Механизм резервирования товара
В текущей реализации выбран самый простой способ – клиент может набрать в корзину столько,
сколько есть на момент создания заказа (поле Article.quantity), но в случае если между
добавлением и оплатой товар был выкуплен, то оплата завершится ошибкой с просьбой убрать\уменьшить позицию.
Автор проекта понимает, что данное решение не слишком клиентоориентированно, (альтернатива – система бронирование товара
на определенное время с подключением Celery+Redis\ValKey.), но поскольку в ТЗ не был четко обозначен этот
момент, то было принято решение отказаться от бизнес-оптимизации и не нагружать проект.
2. Аннотация цен
Поля total_price можно сделать полноценным столбцом таблиц ItemInOrder и Order и денормализовать БД
в пользу скорости, однако это несет за собой усложнение логики при создании\обновлении этих объектов
и усиление валидаций для соблюдения консистентности БД.
Было принято решение отказаться от преждевременной оптимизации.
